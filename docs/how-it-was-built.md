# 이 저장소를 만든 방식

코드는 역할이 나뉜 AI 에이전트들이 썼다. 사람은 무엇을 만들지 정하고, 플랜을 승인하고, 플레이해 보고, PR을 승인한다. 아래는 그 운영 체계다. 실제 규칙 전문은 [AGENTS.md](../AGENTS.md)에 있다.

## 역할

| 역할 | 하는 일 | 사람과의 접점 |
| --- | --- | --- |
| 기획·디자인 | 플랜 작성, 콘텐츠·UX 결정, 리뷰 반영 | 유일하게 직접 대화한다 |
| 개발 리드 | 작업 분할, 테스트 선작성, 구현이 의도대로인지 판단 | 없음 |
| 개발 | 작업 단위 구현 | 없음 |
| QA | 플랜·명세 대비 검증, 버그 리포트 | 결과만 보고한다 |

에이전트끼리 대화는 공유하지 않는다. **플랜 파일, 작업 목록, QA 리포트, PR 코멘트만이 인수인계 수단이다.** 맥락을 말로 넘기지 못하게 하면 남아야 할 것이 파일로 남는다.

개발을 병렬로 돌릴 때만 작업마다 git worktree를 따로 만들고, 개발 리드가 각 결과를 PR 브랜치로 모은다. 순차 작업은 worktree 하나를 재사용한다.

## 단계

하나의 PR이 거치는 길이고, `stage:*` 라벨로 지금 어디인지 추적한다.

```
플랜 작성 → 플랜 리뷰 → 구현 → QA → 플레이테스트 → PR ready → 코드 리뷰 → 사람 승인 → 머지
```

플랜을 먼저 쓰고 리뷰를 받는 이유는, 구현을 다 해놓고 방향이 틀렸다는 걸 알면 되돌릴 게 너무 많기 때문이다. 플랜 단계의 지적이 가장 싸다.

## 리뷰어가 셋이다

- **Codex** — 코드 리뷰. PR 커밋 단위로 요청한다
- **neon** (Antigravity CLI `agy`, 읽기 전용) — 플랜 리뷰와 아트·UX 크리틱. 다른 벤더 모델을 쓰는 게 목적이다. 같은 계열 모델끼리는 같은 것을 놓친다
- **사람** — 결정과 최종 승인

리뷰마다 **어느 커밋을 봤는지**를 PR 본문 표에 남긴다(`단계 · 리뷰어 · 대상 SHA · 판정`). 지적을 반영해 코드가 바뀌면 그 새 SHA도 리뷰됐는지 머지 전에 확인한다. 리뷰어가 한도나 오류로 못 돌면 `skipped(사유)`로 기록하고 진행한다 — 조용히 건너뛰지 않는다.

신원도 분리했다. 에이전트는 별도 계정으로 PR을 열고, 사람은 작성자가 아니므로 GitHub의 Approve를 그대로 쓸 수 있다.

## 규칙은 훅으로 강제한다

지키자고 적어 둔 규칙은 안 지켜진다. 그래서 기계가 막는다.

- 플랜 리뷰는 **훅이 자동으로 부른다.** PR을 열거나 push한 직후, 그 PR이 플랜 리뷰 단계이고 마지막 리뷰 이후 플랜 파일이 바뀌었으면 백그라운드로 실행하고 끝나면 알린다. 에이전트가 부를지 말지 판단하지 않는다
- 스크립트를 거치지 않고 리뷰 코멘트를 직접 달면 훅이 **차단한다**
- PR에 이슈 링크, 크기 라벨, 단계 라벨, 마일스톤이 없으면 CI가 실패한다
- 번들과 정적 에셋이 예산을 넘으면 CI가 실패한다
- `needs-decision` 라벨이 붙은 이슈는 사람이 라벨을 떼기 전까지 PR을 열지 않는다

## 3턴 규칙

플랜 리뷰를 세 번 돌고도 지적이 오면, 플랜을 더 고치지 않고 작업 목록으로 넘긴다.

리뷰어는 언제나 할 말을 찾아낸다. 멈추는 조건을 정하지 않으면 플랜이 영원히 리뷰 상태에 머문다.

## 플레이테스트

Preview 배포는 PR마다 자동으로 만들어지고 PR이 닫히면 삭제된다. 플레이테스트는 그 **Preview URL에서만** 돌린다. production은 실행기가 거절한다 — 실제 접속자 수와 기지 상태를 건드리기 때문이다.

큰 PR은 페르소나(첫 방문자, 폰 캐주얼, PC 개발자)로 돌려 지적을 이슈로 올린다. 씬이나 UI를 건드린 작은 PR은 폰·PC 스크린샷을 찍어 아트 크리틱을 한 번 받는다.

## 측정한다

PR별 단계 소요 시간, 작업량, 사람을 기다린 시간을 스크립트로 집계해 회고에 적는다(`scripts/pr-stats.sh`). 토큰 집계(`scripts/pr-tokens.sh`)는 회고 칸을 폐지하고 수동으로만 쓴다.

커밋 타입 분포는 직접 뽑을 수 있다.

```bash
git log --pretty=%s | sed 's/[(:].*//' | sort | uniq -c | sort -rn
```

기능 커밋보다 문서·도구 커밋이 몇 배 많다. 의도한 결과다 — 사람이 매번 지시하는 대신 규칙과 검사를 코드로 박았기 때문이고, 그 값이 이 프로젝트에서 가장 크게 돌아온 투자였다.

## 문서가 썩는 것도 검사한다

문서는 코드보다 빨리 낡는다. 그래서 마일스톤이 끝날 때와 회고 PR마다 `doc-lint`를 돌려, 문서의 주장(이슈 참조, 열거 목록, 날짜, 명령어, 수치)을 GitHub 이슈·PR·git·코드의 실제 상태와 대조한다. 어긋난 것은 이슈로 올린다. 자동으로 고치지는 않는다.

같은 이유로 이 문서와 README에는 고정된 수치를 쓰지 않았다. 숫자가 필요하면 뽑는 방법을 적어 둔다.
